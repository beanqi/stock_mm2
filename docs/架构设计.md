# stock_mm 整体架构设计

配套文档：[`策略设计.md`](./策略设计.md)。本文只讨论工程架构（代码结构、模块划分、数据流、状态机），不重复策略公式。

---

## 1. 设计目标与约束

| 目标 | 架构含义 |
| --- | --- |
| 策略逻辑必须可测试、可诊断 | 核心逻辑写成**纯函数式状态机**（无 IO、无 `SystemTime`、无随机），行为完全由输入事件决定，单测可精确断言动作序列 |
| 多交易所、多标的、多策略实例 | 交易所走 trait 抽象；策略实例是独立 actor，互不共享可变状态 |
| 低频 Requote，但跳价时要快 | 报价采用**声明式目标状态 + 协调器 diff**，而不是散落各处的 `place/cancel` 调用 |
| 不能重复下单/重复撤单 | 订单有显式生命周期状态机 + in-flight 追踪 + 幂等 `client_order_id` |
| 进程崩溃后不能留下裸单裸仓 | 启动时强制与交易所对账（open orders + position），本地事件日志可重放 |
| 价格精度不能出错 | 全程定点小数（`rust_decimal` 或 scaled `i64`），tick/lot 取整集中在一个模块 |
| 风险要能一键收口 | 风控是**独立的门控层**，输出"允许买/允许卖/只减仓/全平"，策略逻辑不自己决定要不要冒险 |
| 下单与回报全走 WebSocket | 需要 WS 请求/响应 id 关联层、连接级限速、以及"结果未知"态的显式处理；HTTP 只保留启动引导与兜底 |

非目标（当前版本）：不做库存偏移报价（文档 §7 明确）、不做多腿对冲、不做跨交易所搬砖执行。

## 2. 分层架构总览

```text
┌───────────────────────────────────────────────────────────────────────┐
│  L5 接入层   mm-api (HTTP/WS)   mm-telemetry (metrics/log)            │
├───────────────────────────────────────────────────────────────────────┤
│  L4 运行时   mm-engine: Supervisor / StrategyActor / OrderGateway     │
│              / TimerWheel / Recovery        mm-risk: 全局风控 actor    │
├───────────────────────────────────────────────────────────────────────┤
│  L3 策略核心 mm-strategy (纯逻辑，零 IO)                               │
│              pricing → quote → position/exit → risk gate              │
├───────────────────────────────────────────────────────────────────────┤
│  L2 行情/执行 mm-marketdata (盘口聚合/失效检测/FX)                     │
│              mm-exchange (trait + WS 会话/RPC/限速 基础设施)           │
│              exchanges/* (各交易所适配器)                              │
├───────────────────────────────────────────────────────────────────────┤
│  L1 基础     mm-types (领域类型/Clock)  mm-config  mm-store (journal)  │
└───────────────────────────────────────────────────────────────────────┘
```

依赖方向严格向下，**L3 只依赖 L1**。L3 不知道"交易所"、"HTTP"、"tokio"的存在，它只消费 `Event`、产出 `Action`。

## 4. 核心数据流

```text
 参考行情 WS ─┐
 挂单行情 WS ─┼─► Feed Router ──┐    ┌────────────────────────┐
 FX 源 ───────┘   (合并/扇出)    │    │ StrategyActor (单线程)  │
                                ├─►  │  ┌──────────────────┐  │ ──Action──► OrderGateway ──► Trading WS ─► 交易所
 私有推送 WS ───────────────────┤Event│  │ StrategyCore (纯) │  │             (优先级/限速/RPC)
 (订单/成交/持仓/资产)           │    │  └──────────────────┘  │                   │
 定时器 / 控制指令 ──────────────┘    └───────────┬────────────┘                   │
        ▲                                        └──► Journal / Metrics / API      │
        └──────── ReqOutcome(Accepted/Rejected/Unknown) ──────────────────────────┘
```

**四条 WS 链路**：参考市场行情（公有）、挂单市场行情（公有）、私有推送（订单/成交/持仓/资产）、交易链路（下单出口）。行情与私有推送是订阅流，交易链路是请求/响应流，职责不混用。

### 4.1 事件与动作（L3 唯一接口）

```rust
pub enum Event {
    RefBook(BookUpdate),          // 参考市场盘口
    MakerBook(BookUpdate),        // 挂单市场盘口（快平、spread 采样、post-only 保护都要用）
    Fx(FxUpdate),
    Exec(ExecReport),             // 私有推送：Ack / Reject / PartialFill / Fill / Canceled / Expired
    PositionSync(PositionSnapshot), // 交易所净仓推送，用于对账
    Asset(AssetUpdate),           // 余额 / 权益 / 可用保证金推送，供风控与下单量计算
    ReqOutcome { coid: ClientOrderId, result: ReqResult }, // 交易链路响应：Accepted / Rejected / Unknown
    Timer(TimerId),
    Link { venue: VenueId, kind: LinkKind, up: bool }, // MarketData / Private / Trading 分开上报
    Control(ControlCmd),          // Start / Stop / Flatten / ConfigUpdate
}

pub enum Action {
    Place(PlaceReq),
    Cancel { coid: ClientOrderId },
    Amend  { coid: ClientOrderId, px: Px, qty: Qty },
    CancelAll { venue: VenueId, symbol: SymbolId },
    SetTimer { id: TimerId, at: Ts },
    ClearTimer(TimerId),
    Emit(TelemetryEvent),
}

pub trait StrategyCore {
    /// 纯函数：不做 IO、不读时钟（now 由外部注入）、不 spawn。
    fn on_event(&mut self, now: Ts, ev: &Event, out: &mut Vec<Action>);
    fn snapshot(&self) -> StateSnapshot; // 给 API / 诊断
}
```

这条接口是整个架构的收敛点：实盘运行与单元测试都只通过它驱动策略。

两点约定：**私有推送是订单与持仓的唯一真相来源**，交易链路的响应只用来判断"请求有没有被受理"，不用来更新订单状态（响应与推送可能乱序到达）；`ReqResult::Unknown`（超时或连接断开）必须是显式一等状态，槽位保持 `Pending` 并等待私有推送或主动查询收敛，绝不假设失败后直接重发。

### 4.2 一次 tick 的处理链路

参考盘口更新 →
`refprice`（mid + 合法性）→ `normalize`（FX × multiplier）→ `spread`（滚动中位数/MAD 更新）→ `fair`（FairPrice + 跳价检测）→ `risk::guards + limits`（得到 `QuotePermission`）→ `quote::grid`（目标买卖档位）+ `position::exit`（目标退出单）→ `quote::reconcile`（与本地订单视图 diff）→ `Vec<Action>`。

关键点：**网格单和退出单合并进同一个协调器**，否则两者会互相撤单、互相穿越。

## 5. 报价协调器（工程核心）

### 5.1 槽位模型

所有挂单归属一个"槽位"，槽位是幂等键，直接编码进 `client_order_id`：

```rust
struct SlotKey { purpose: Purpose, side: Side, index: u8 }
enum Purpose { GridEntry, Exit(LotId) }
// client_order_id = {strategy_id}-{purpose}-{side}-{index}-{seq}
```

每个槽位在任意时刻最多一个活跃订单 + 最多一个 in-flight 请求。这一条约束解决了绝大多数做市系统的"重复挂单 / 幽灵单"问题。

### 5.2 diff 规则

对每个槽位比较 `desired: Option<DesiredOrder>` 与 `live: SlotState`：

| desired | live | 动作 |
| --- | --- | --- |
| Some | Empty | `Place` |
| None | Live | `Cancel` |
| Some | Live，偏离 ≤ RequoteThreshold 且数量一致 | **不动**（保住排队位置） |
| Some | Live，偏离 > RequoteThreshold | 支持改单则 `Amend`，否则 `Cancel` → 下个事件再 `Place` |
| 任意 | PendingNew / PendingCancel / Unknown | 不动，等回报或对账结果（见 6.2） |

跳价路径独立：`fair` 检出跳价（|ΔP_ref| > JumpThreshold）时，先发 `CancelAll`（比逐单撤更快、更省限速），进入短暂 `cooldown`，冷却结束才重新铺单。

### 5.3 必须守住的不变量

- **不自成交**：`max(所有买单价) < min(所有卖单价)`，退出单与网格单一起参与检查；冲突时按优先级（退出 > 网格）裁掉另一边。
- **不穿越对手价**（post-only 保护）：买单价 ≤ 挂单市场 Ask1 - tick，卖单价 ≥ Bid1 + tick，否则会被 post-only 拒单。
- **不超限**：铺单后的潜在净仓不得突破 `MaxLong/MaxShort`（成交前就要算进去，而不是成交后才发现超限）。
- **取整方向**：买单价向下取整到 tick，卖单价向上取整，数量向下取整到 lot；退出单取整必须保证**不亏掉目标利润**。

## 6. 关键状态机

### 6.1 策略生命周期

```text
Init ─► Warmup ─► Running ◄──► Degraded(ReduceOnly)
                    │                │
                    └──► Flattening ─┘ ──► Stopped
```

- `Warmup`：NaturalSpread 窗口样本不足（未满 2 分钟 / 未达最小样本数）时**只观察不报价**。
- `Degraded`：命中策略文档 §8 任一保护条件 → 撤掉所有开仓单，仅保留退出逻辑。
- `Flattening`：人工或全局风控触发，强制清仓后停机。

### 6.2 订单状态机（每槽位）

```text
Empty ─Place─► PendingNew ─Ack─► Live ─┬─Amend─► PendingAmend ─► Live
   ▲              │ Reject             ├─Cancel─► PendingCancel ─► Empty
   │              │                    └─Fill/PartialFill─► (Live | Empty) + 产出 Lot
   │              ▼ 超时 / 交易链路断开
   └────── Unknown ──对账查询──► (Live | Empty)
```

走 WS 下单后 `Unknown` 是常态路径而不是异常分支：任何 `Pending` 状态都带超时定时器，超时或链路断开即转 `Unknown`，只能由私有推送或对账查询收敛。`Unknown` 槽位**既不能重发也不能当成已撤**，否则会出现双份挂单或裸单。

### 6.3 退出状态机（每 Lot，对应策略文档 §6）

```text
Open(MakerTP @ entry±TakeProfit)
  ├─ 成交 ─────────────────────────────► Closed
  ├─ t > FastExitTimeout ──► FastMaker(贴 Bid1/Ask1，随盘口跟价)
  │                            ├─ 成交 ──► Closed
  │                            └─ t > ForceExitTimeout ──► TakerExit ──► Closed
  └─ 相对 FairPrice 浮亏 > MaxLoss ──────► TakerExit（任何阶段都可跳转）
```

止损用 **FairPrice** 而非本地最新成交价，和策略文档一致；这样低流动性市场的插针不会误触发。

### 6.4 持仓表示

交易所侧是**净仓**，策略侧按 **Lot（每笔成交一个批次，FIFO）** 管理，因为止盈价和超时时刻都是"按成交"定义的。`position::book` 负责两者对账：

- `sum(lots) != 交易所净仓` → 记录 drift 指标，以交易所为准调整/合成残差 Lot，并告警。
- 部分成交生成部分 Lot；同价位的多个 Lot 可以合并成一张退出单（减少订单数），但超时计时按最早 Lot 算。

## 7. 风控与保护层

风控不内嵌在报价逻辑里，而是一个独立函数，输出门控结果：

```rust
struct QuotePermission {
    allow_new_buy:  bool,
    allow_new_sell: bool,
    max_new_qty:    Qty,
    force_cancel_all: bool,
    force_flatten:    bool,
    reason: Option<GuardReason>,   // 打点/前端展示
}
```

`guards.rs` 逐条实现策略文档 §8，每条都是显式的、可单测的判定：盘口失效（交叉/零价/单边缺失）、行情延迟（本地时钟 - 交易所时间戳 > 阈值）、参考市场跳价、`|Spread_t - NaturalSpread| > K·SpreadVol`、停牌/闭市时段、仓位触顶。

WS 化之后额外多四条链路类门控：任一行情链路 down 或 stale、私有推送链路 down（订单状态不可信）、交易链路 down（发不出撤单，此时也不该继续持有挂单敞口）、存在未收敛的 `Unknown` 槽位。前三条都直接进 `Degraded`。

`mm-risk` 是跨策略的第二道闸：总敞口、单交易所敞口、日内最大亏损、异常撤单频率，触发后向所有 `StrategyActor` 广播 `Control::Flatten`/`Stop`。两层分工明确——策略内看"这个标的现在能不能报"，全局看"整个进程是不是该收手"。

## 8. WebSocket 链路设计

全链路 WS，HTTP 只在两处出现：启动时拉 instrument 规格，以及 WS 查询能力缺失时的对账兜底。

### 8.1 连接拓扑

| 链路 | 数量 | 内容 | 断开影响 |
| --- | --- | --- | --- |
| 参考行情 | 每参考市场 1 | TopOfBook / L2 增量 | FairPrice 失效 → 撤开仓单，进 `Degraded` |
| 挂单行情 | 每挂单市场 1 | TopOfBook / L2 增量 | 无法做 post-only 保护与快平跟价 → `Degraded` |
| 私有推送 | 每账户 1 | 订单、成交、持仓、资产 | 订单状态失去真相来源 → 停止新开仓，重连后强制对账 |
| 交易链路 | 每账户 1～N | 下单 / 改单 / 撤单请求与响应 | 无法下撤单 → 立即停止报价；恢复后先对账再报价 |

**交易链路与私有推送分开连接**：行情或成交回报的洪峰不应该排在下单请求前面。如果交易所允许多条交易连接，再单独保留一条**只发撤单与全平的应急连接**，保证 kill switch 不会排在一堆 requote 后面。

### 8.2 WS RPC 层（`ws/rpc.rs`）

WS 下单是异步请求/响应，需要一个最小 RPC 层：

```rust
struct Pending { coid: ClientOrderId, kind: ReqKind, sent_at: Ts, deadline: Ts }
// req_id -> Pending，响应到达或超时后移除
```

- **id 关联**：每个请求带自增 `req_id`，同时携带 `client_order_id`；响应按 `req_id` 匹配，超时按 `deadline` 扫描。
- **超时 → Unknown**：超时不等于失败。产出 `ReqOutcome{ Unknown }`，由对账流程（私有推送或查询）收敛真实状态。
- **幂等重试**：`client_order_id` 由槽位确定性生成（`{strategy}-{purpose}-{side}-{idx}-{seq}`），重发同一 id 要么被交易所判重拒绝、要么落到同一订单，都不会产生双份挂单。
- **连接断开**：所有 pending 立即转 `Unknown`，同时上报 `Link{ Trading, up: false }`。
- **批量优先**：支持批量下单/批量撤单的交易所必须用批量接口，网格铺单天然是批量语义，能显著省连接级限速额度。
- **热路径开销**：报文用预置模板 + 定长字段替换，避免每次 `serde_json` 全量序列化；单条连接的写入串行化，避免交错帧。

### 8.3 心跳、重连与缺口处理

- **心跳**：按交易所要求的间隔发 ping，同时把 RTT 当作链路健康指标；连续丢失 pong 即主动重连，不等 TCP 超时。
- **重连**：指数退避 + 抖动；私有链路重连后必须**重新鉴权 → 重新订阅 → 强制对账**，对账完成前策略停留在 `Degraded`。
- **序号缺口**：行情增量检测 seq gap → 重取快照；私有推送若带序号，缺口同样触发对账。
- **时钟**：用交易所推送时间戳与本地时间的差值做延迟判定（策略文档 §8 的行情延迟阈值），并持续监控时钟漂移。

### 8.4 限速与背压

连接级令牌桶（WS 通常按连接限 op/s），队列按优先级划分：**撤单/全平 > 退出单 > 网格开仓单**。额度紧张时先丢弃网格 requote（不报价不亏钱），绝不丢撤单。行情侧反向处理：只保留最新盘口，积压直接合并丢弃旧帧。

## 9. 数值与交易所细节

- **不用 f64 做价格**：`Px`/`Qty` 用 `rust_decimal` 或 scaled `i64`；只有统计量（spread、MAD）允许在内部用 f64/bps 整数。
- **NaturalSpread 滚动窗口**：按 100ms 时间桶降采样（2 分钟 ≈ 1200 样本），用"有序 `Vec` + 时间 `VecDeque`"实现 O(log n) 插入 + O(1) 取中位数；样本量再大就换 bps 直方图（O(1) 更新，中位数与 MAD 都能直接读）。
- **费率进公式**：`TakeProfit` 必须扣掉双边手续费/返佣，否则名义 0.12% 可能是负收益。费率作为 instrument 静态属性注入定价层。
- **Amend vs Cancel+Place**：能改单的交易所优先改单（降量改单通常保留排队位置）；不支持则退化为撤后重挂，并在指标里区分两者的成交率差异。
- **行情 stale 标记**：任一市场出现 seq gap、心跳丢失或推送延迟超阈值，立刻标记 stale 并触发 §7 门控，而不是继续用旧盘口报价。

## 10. 并发与进程模型

单进程、tokio 多线程运行时，任务划分：

| 任务 | 数量 | 职责 |
| --- | --- | --- |
| WS session task | 每条 WS 连接 1（读写各一半） | 收发帧、心跳、重连、解析成 `Event` |
| Feed router | 每行情主题 1 | 扇出 + 合并，供多策略共享同一订阅 |
| Strategy actor | 每策略实例 1 | 串行消费 `Event`，驱动 `StrategyCore` |
| Order gateway | 每账户 1 | 汇总所有策略的 `Action`，按优先级限速、维护 in-flight 与 WS RPC pending |
| Risk actor | 1 | 全局风控 |
| API / metrics | 各 1 | 对外接口 |

策略实例之间**不共享可变状态**，只通过 channel 通信；因此不需要在热路径上加锁，也让"一个策略卡死不影响其他策略"成立。

## 11. 崩溃恢复与对账

启动顺序（`recovery.rs`）：

1. 加载配置，拉取 instrument 规格（这一步走 HTTP，静态数据、只取一次）。
2. 建立四条 WS 链路并完成鉴权订阅；查询 open orders 与 positions（优先用 WS 查询，无此能力才退回 HTTP 快照）。
3. 按 `client_order_id` 前缀识别自家订单：能映射到槽位的**接管**，识别不出的按配置决定（默认撤单并告警）。
4. 用交易所净仓 + 平均开仓价重建 Lot（丢失了原始成交时刻，退出计时从恢复时刻起算，并按保守策略直接进 `FastMaker`）。
5. 进入 `Warmup` 重新积累 spread 样本，样本足够才恢复报价。

**运行期对账**同样需要：私有链路每次重连、出现 `ReqResult::Unknown`、或本地订单视图与推送不一致时，都触发一次增量对账（查开放订单 + 持仓），把本地槽位与交易所拉回一致；对账期间只允许撤单和平仓。

运行期所有 `Event`/`Action` 顺序写 journal（`mm-store`），用于事故复盘、与交易所对账，以及重建"当时为什么这么报价"。

## 12. 配置模型

`config/strategies/*.toml` 与策略文档 §9 一一对应，分四组：`[market]`（maker/ref 交易所与 symbol、FX、multiplier）、`[pricing]`（spread 窗口、网格档位表、requote/jump 阈值）、`[exit]`（TakeProfit、两级超时、MaxLoss）、`[risk]`（各类仓位与单量上限、最大延迟、最大异常价差、K 值）。

要求：serde 反序列化后做**范围校验与逻辑校验**（如 `RequoteThreshold < Grid`、`TakeProfit > 双边费率`、`FastExitTimeout < ForceExitTimeout`），校验失败拒绝启动；热更新走"生成新配置 → 校验 → 由 actor 在事件边界原子切换"，并区分"可热改参数"与"需重启参数"（交易所/symbol 属于后者）。

## 13. 可观测性

- **结构化日志**：`tracing`，每条带 `strategy_id` / `slot` / `coid`，决策日志记录"为什么没报价"（`GuardReason`）——这是做市系统最常被问的问题。
- **指标**：FairPrice、NaturalSpread、SpreadVol、挂单数、requote 频率、撤单/成交比、Maker 成交占比、各退出阶段占比（Maker 止盈 / 快平 / Taker 强平比例是策略健康度的核心指标）、限速余量、行情延迟。
- **链路指标**（WS 全链路后必备）：每条连接的 ping RTT、重连次数与最近重连时间、下单请求往返延迟分位数、`Unknown` 结果计数、pending 请求数、对账触发次数与修正条数。`Unknown` 和对账修正条数长期非零说明链路或幂等设计有问题。
- **PnL 归因**：拆成价差收益、手续费/返佣、逆向选择损失（成交后 N 秒 FairPrice 漂移）、强平滑点，四项分开看才能判断参数该往哪调。

## 14. 测试策略

不做模拟撮合，全部依赖纯逻辑测试 + 真实小资金灰度。

| 层次 | 方式 |
| --- | --- |
| 单元 | 定价、滚动中位数、取整、grid 生成、reconcile diff 表逐项覆盖 |
| 状态机 | 给定事件序列断言动作序列（`StrategyCore` 是纯的，断言精确到 `Vec<Action>`） |
| 属性测试 | 随机事件流下检查不变量：买价永不高于卖价、不超仓位上限、无重复槽位订单、无裸仓 |
| 报文解析 | 用**录制的真实 WS 报文**做 fixture，覆盖各类回报、拒单原因、异常帧 |
| 链路 | RPC 层单测：响应乱序、响应丢失转 `Unknown`、断连时 pending 清理、限速优先级 |
| 灰度 | 真实交易所 + 最小单量 + 收紧的风控上限，先只验证链路与对账，再逐步放开参数 |

## 15. 实施路线图

| 里程碑 | 内容 | 产出判据 |
| --- | --- | --- |
| M0 | `mm-types` + `mm-config` + instrument 取整 | 价格/数量运算与校验有测试覆盖 |
| M1 | `mm-exchange` WS 会话层 + 两个市场的行情链路 + `mm-marketdata` | 能稳定输出 ref mid，断线自愈、seq gap 可恢复 |
| M2 | 私有推送链路 + 交易链路 + `ws/rpc` + `order_gateway` | 手工指令能下撤单，回报与 `Unknown` 处理正确 |
| M3 | `pricing`（spread/fair/跳价）+ 指标面板 | 只观察不下单，NaturalSpread 曲线合理 |
| M4 | `quote`（grid + reconcile）+ 订单状态机 | 小资金实盘能稳定双边挂撤，requote 频率符合预期 |
| M5 | `position` + `exit` 三级退出 + `risk` 门控 | 不留裸仓，三档退出占比可观测 |
| M6 | `mm-store` journal + `recovery` + `mm-api` | 可重启对账、可复盘、可前端配置多策略 |

顺序上把 WS 交易链路（M2）提到定价之前：既然直接实盘，链路可靠性和对账正确性是先决条件，用手工指令把下单、改单、撤单、断线重连、`Unknown` 收敛这几条路径跑通，再让策略自动发单。

## 16. 待确认的开放问题

1. **WS 交易能力**：挂单市场的 WS 是否支持下单/改单/撤单/批量撤单、是否支持 WS 查询开放订单与持仓（决定第 11 节对账能否完全脱离 HTTP）、单连接 op/s 限额、是否允许多条交易连接。
2. 挂单市场是否支持 amend、post-only、以及是否有自成交保护（直接影响第 5 节协调器实现）。
3. 私有推送是否带序号或可检测丢失，以及是否会推送资产/保证金变化（没有的话风控只能靠定期查询兜底）。
4. 参考市场闭市/停牌时段与挂单市场是否一致（跨市场时段错配时的默认行为）。
5. 净仓 vs 双向持仓模式、以及是否有强平/保证金约束需要进风控层。
6. Lot 级退出 vs 净仓单张退出：前者贴合策略文档语义，后者订单数更少，需确认交易所挂单数限制。
7. 目标标的数量级（几个还是几百个），决定是否需要把 `StrategyActor` 做成分片调度，以及一条交易连接是否够用。
